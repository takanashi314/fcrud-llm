## 5. 判断の理由

- **初回コミットを main に直接入れた理由**: リポジトリにコミットが1つもなく、PR の base になるブランチが存在しないため。main への直接コミットは**この初回だけの例外**で、2回目以降は必ず PR を経由する。
- **ブランチ名を `master` から `main` に変えた理由**: 計画書のブランチ戦略、GitHub の現在の標準、py-ci-tpl / flaskboard と揃えるため。
- **Issue の自動クローズの扱いを明記した理由**: `Closes #n` は main へのマージでしか動かない。3段構成では dev → feature の PR で issue が閉じないため、ルールを決めておかないと flaskboard と同じく open のまま残ってしまう。
- **テストに SQLite を使わない理由**: 本番の PostgreSQL と挙動（型、制約、タイムゾーン）が違い、「テストは通るのに本番で落ちる」ことを防ぐため。
- **ブランチを削除しない方針への補足**: 一般的な実務では削除することが多い。この点は計画書 §6.5 に注記した。
